# TEMPLATE-UPGRADE: 待人工确认项应包含 AI 建议与依据

> 类型：派生项目中发现的模板优化提案。
> 状态：待评估 / 待回流。
> 关联：`ai/document-lifecycle-rules.md`、`ai/doc-standards/00-09`、`ai/prompts/docs/00-generate-or-complete-docs.md`、`ai/prompts/review/10-docs-checklist.md`、`ai/project-rules.md`。

## 1. 背景与问题

当前文档体系鼓励在 `docs/00-09`、`docs/design/*`、项目规则和开发计划中保留“待人工确认项”，用于避免 AI 越权替用户做业务、技术、资源或合规决策。

这个机制是必要的，但目前常见输出形态偏向“问题清单”：

```markdown
## 待人工确认

1. Phase1 存储采用 JSON / SQLite / 内存 / PostgreSQL 哪一种。
2. Docker 是否必须修复后再进入 Sprint-1。
3. 是否允许真实发送飞书通知。
```

这类写法能暴露不确定性，却没有充分发挥 AI 辅助分析的价值。用户之所以借助 AI，往往正是因为部分领域经验不足或信息不完整；如果 AI 只列问题，不给建议、依据和取舍分析，用户仍需要自行判断，后续也容易出现反复确认和返工。

因此，模板需要明确：待人工确认项不应只是问题列表，还应包含 AI 的建议、依据、备选方案和影响分析。AI 不能替用户最终拍板，但应提供可审查的推荐口径，帮助用户做选择。

## 2. 设计目标

- 保留“AI 不越权决策”的红线。
- 提升待确认项的可操作性，避免只问问题不辅助分析。
- 帮助非专业用户理解每个选择的依据、成本、风险和阻塞关系。
- 让后续 AI 会话能根据“建议 + 依据 + 用户确认”稳定续接，不重复追问。
- 将确认结果更容易回填到 PRD、技术方案、开发计划、任务单和续接文件。

## 3. 建议规则

### 3.1 待确认项最低结构

建议模板要求所有正式文档中的“待人工确认项”尽量采用结构化表格，而不是纯问题列表。

最低字段建议如下：

| 字段 | 说明 |
|---|---|
| 待确认项 | 需要人确认的问题。 |
| AI 建议 | AI 推荐的默认口径或优先选项。 |
| 建议依据 | 来自上游文档、阶段目标、资源约束、风险边界或通用经验的理由。 |
| 备选方案 | 可选的其他路径。 |
| 取舍影响 | 推荐方案与备选方案的成本、风险、阻塞或后续影响。 |
| 阻塞关系 | 是否阻塞当前 Sprint / Phase；不阻塞时说明可延后到哪个阶段。 |

### 3.2 推荐格式

```markdown
## 待人工确认

| ID | 待确认项 | AI 建议 | 建议依据 | 备选方案 | 取舍影响 / 阻塞关系 |
|---|---|---|---|---|---|
| C-001 | Phase1 存储采用哪种方式？ | Sprint-1 先用 JSON / 内存。 | Sprint-1 目标是 API 骨架；当前 Docker / PostgreSQL 不是前置条件；API 契约可先保持稳定。 | SQLite、PostgreSQL。 | JSON / 内存最快但非生产；SQLite 更接近持久化；PostgreSQL 最接近目标但会引入环境阻塞。 |
```

### 3.3 AI 行为约束

- AI 应给出建议，但必须标明“建议 / 推荐 / 默认口径”，不得伪装成用户已确认事实。
- AI 的建议必须附依据，不得只写“建议选 A”。
- AI 应说明备选方案和取舍影响，避免单一路径诱导。
- 高风险事项必须保留人工确认，不得因给出建议而视为自动确认。
- 若信息不足，AI 可以给“临时建议 + 需补充的信息”，并说明缺失信息会如何影响判断。
- 一旦用户确认，AI 应把确认结果回填到相关文档或续接文件，并移出“待确认”或标记为“已确认”。

## 4. 适用范围

建议适用于以下文档区域：

- `docs/00-09` 的待人工确认章节。
- `docs/design/*` 的设计决策与待确认章节。
- `docs/decisions/*` 中 ADR 的待确认后续动作。
- `docs/08-dev-plan.md` 的 Sprint 前置条件与待确认项。
- `tasks/task-*.md` 的阻塞项、禁止事项和验收口径。
- `.ai/session-handoff.md` 中的待确认问题清单。

不要求所有临时对话都使用完整表格；但一旦写入正式文档或可续接状态文件，应尽量保留建议与依据。

## 5. 拟改范围

### 规则文件

- `ai/document-lifecycle-rules.md`：补充“待确认项必须包含建议、依据和影响分析”的文档生命周期规则。
- `ai/global-rules.md`：在“AI 不可自主扩展需求 / 先设计后实现”附近补充 AI 可提供建议但不得替人确认的边界。
- `ai/session-rules.md`：续接文件中的待确认项建议包含 AI 推荐口径与阻塞关系。

### 文档标准

- `ai/doc-standards/00-09`：在核心文档标准中统一“待人工确认”章节结构。
- 可为不同文档给出轻量变体：需求类偏业务依据，技术类偏资源 / 风险依据，验证类偏阻塞与验收影响。

### 生成提示词

- `ai/prompts/docs/00-generate-or-complete-docs.md`：生成 `docs/00-09` 时，待确认项必须输出建议、依据、备选方案和影响。
- `ai/prompts/docs/04-edit-single-doc.md`：编辑单文档时，如果新增待确认项，也要补齐建议和依据。
- `ai/prompts/docs/07-sync-docs-from-code.md`：代码回填文档时，如果发现未确认决策，应给出建议和影响，而不是只列问题。

### 审查提示词

- `ai/prompts/review/10-docs-checklist.md`：新增检查项：待确认项是否只有问题、缺少建议 / 依据 / 影响；若缺失，应退回补充。
- 审查输出应区分：
  - “AI 已给建议但待人确认”。
  - “用户已确认，可回填为项目事实”。
  - “信息不足，需补充输入后再建议”。

### 快捷命令

- `ai/commands/README.md`：补充文档生成 / 审查命令对待确认项结构的要求。
- 相关命令如 `docs-system-audit`、`sprint-summary`、`scenario` 可在续接要求中记录建议与阻塞关系。

## 6. 版本影响

建议作为后续 minor 版本落地。

理由：该变更会影响文档生成质量、审查标准和 AI 与用户的确认协作方式；它不改变目录结构，但会改变 `docs/00-09` 和详细设计文档的默认内容结构。

## 7. 验收口径

- 新生成的 `docs/00-09` 中，待确认项不是纯问题列表，而包含 AI 建议和依据。
- 文档审查能发现“只列待确认问题但未给建议 / 依据 / 影响”的情况。
- 用户确认某项后，AI 会把该项从待确认迁移到“已确认口径 / 当前决策 / 文档事实”中。
- 高风险或合规事项即使有 AI 建议，也仍需人工确认，不会被自动写成已确认事实。
- 续接文件能记录未确认项的推荐口径、阻塞关系和下一步确认动作。

## 8. 风险与缓解

- **AI 建议被误认为最终决策**：用字段名明确“AI 建议 / 待人工确认”，并要求用户确认后才能回填为事实。
- **文档变长**：允许按重要性裁剪；低风险确认项可简写，但关键业务、技术、资源和合规项必须完整。
- **建议依据不足**：要求 AI 标明依据来源；若依据不足，应写“临时建议”和“缺失信息”。
- **过度诱导用户**：必须列备选方案和取舍影响，避免只给单一路径。
- **确认结果散落**：用户确认后应同步更新正式文档或续接文件，避免旧待确认项继续误导后续会话。
