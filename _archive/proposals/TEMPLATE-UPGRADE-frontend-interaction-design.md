# TEMPLATE-UPGRADE: 前端交互设计文档触发规则与标准结构

> 类型：派生项目中发现的模板优化提案。
> 状态：已落地于 ai-project-template v1.30.0；派生项目已同步并评估覆盖，归档留痕。
> 关联：`ai/global-rules.md` 中前端启用规则、`ai/prompts/docs/00-generate-or-complete-docs.md` 中演示形态判断、`ai/prompts/review/10-docs-checklist.md` 文档审查清单。

## 1. 背景与问题

当前模板已能按项目形态判断是否保留 `frontend/`，并要求独立 Web / 移动端演示类项目在 `docs/04-architecture.md`、`docs/05-tech-spec.md` 中体现前端架构与技术方案。

但对于需要真实页面交互的项目，模板尚未明确：

- 什么时候必须补充前端交互设计文档。
- 前端交互设计应放在哪个目录、是否占用 `docs/00-09` 编号。
- 页面流、组件、状态、错误提示、空状态、权限 / 风险文案、接口依赖和验收路径应如何记录。
- 审查时如何判断“前端技术方案已写”与“前端交互足以指导开发”之间的差异。

结果是派生项目容易只在架构或技术方案中写到页面名称、技术栈和 API 调用，却缺少可指导前端实现和验收的交互细节。后续 AI 编码时可能根据主观理解补页面、补状态、补文案，违反“先设计后实现”和“AI 不可自主扩展需求”的原则。

## 2. 设计目标

- 不增加所有项目的固定文档负担，保持 `docs/00-09` 核心编号稳定。
- 对独立 Web、移动端、小程序、桌面端等 UI 型项目，提供明确的交互设计触发规则。
- 让前端开发前具备足够设计输入，减少 AI 在编码阶段临场补交互。
- 统一页面结构、用户路径、状态模型、边界文案、接口依赖和验收口径。
- 与现有文档链路兼容：`Scenario → 用户需求 → SRS → PRD → 架构 → 技术方案 → 详细设计 → 开发计划 → 代码`。

## 3. 建议方案

### 3.1 文档定位

不建议新增固定编号文档，也不建议把前端交互设计纳入所有项目必备项。

建议将其定义为 `docs/design/` 下的条件性详细设计文档：

```text
docs/design/frontend-interaction.md
```

如果项目存在多个差异很大的前端入口，也允许按入口拆分：

```text
docs/design/customer-app-interaction.md
docs/design/admin-console-interaction.md
docs/design/mobile-app-interaction.md
```

### 3.2 触发条件

当项目满足以下任一条件时，应在开发前补充前端交互设计：

- 交付形态包含独立 Web、移动端、小程序、桌面端或其他可点击 UI。
- 存在多页面、多角色、多入口或跨页面流程。
- 存在复杂表单、筛选、列表、详情、审批、状态流或异常处理。
- 验收需要按点击路径、页面状态或用户操作完成。
- 用户需求、PRD 或愿景中出现“页面、界面、点击、扫码、表单、看板、控制台、手机、H5、Web、App、小程序”等交互信号。

当项目仅为 CLI、后端 API、批处理脚本、纯消息通道内机器人，且没有可视化操作界面时，可以不创建该文档，但应在 `ai/project-rules.md` 或 `docs/05-tech-spec.md` 中说明不需要前端交互设计的原因。

## 4. 建议文档结构

推荐 `docs/design/frontend-interaction.md` 使用以下结构：

```markdown
# Frontend Interaction Design

## 0. 文档元信息

- 状态：草稿 / 已确认
- 覆盖范围：入口、角色、页面
- 上游依据：PRD / SRS / Architecture / API Spec

## 1. 目标与范围

- 本文覆盖哪些前端入口与用户角色
- 本阶段明确不做哪些交互

## 2. 页面 / 路由清单

| 页面 ID | 页面 / 路由 | 用户角色 | 入口 | 核心任务 | 关联 REQ / API |

## 3. 用户路径

| Flow ID | 触发入口 | 主路径 | 分支 / 异常 | 完成状态 | 关联验收 |

## 4. 页面结构

按页面描述：区域、主要组件、可操作元素、展示字段、跳转关系。

## 5. 状态模型

覆盖 loading、empty、error、disabled、success、warning、risk、offline、mock 等状态。

## 6. 表单与校验

字段、默认值、必填规则、格式校验、提交反馈、失败恢复。

## 7. 文案与边界提示

空状态、错误提示、权限提示、风险提示、免责声明、Mock / Demo 标识。

## 8. 接口依赖

页面到 API 的映射、请求时机、关键字段、失败处理、降级策略。

## 9. 响应式与可访问性

目标尺寸、键盘操作、可读性、基础无障碍要求。

## 10. 验收路径

按用户路径列出可手工验证或自动化测试的点击路径。

## 11. 待确认项

```

## 5. 拟改范围

### 规则文件

- `ai/global-rules.md`：在 `frontend/` 启用说明中补充“UI 型项目应按触发条件补充 `docs/design/*interaction*.md`”。
- `ai/document-lifecycle-rules.md`：补充详细设计层可包含条件性前端交互设计，不占用 `docs/00-09` 编号。
- `ai/project-rules.md` 模板 / 生成口径：在项目形态裁剪时说明是否需要前端交互设计。

### 文档标准

- `ai/doc-standards/04-architecture.md`：在前端组件 / 页面型系统中要求指向交互设计文档。
- `ai/doc-standards/05-tech-spec.md`：区分技术方案与交互设计，技术方案写技术选型和实现策略，交互设计写用户路径和页面状态。

### 提示词

- `ai/prompts/docs/00-generate-or-complete-docs.md`：在“演示形态”判断后增加“是否需要前端交互设计文档”的判断与生成步骤。
- `ai/prompts/docs/04-edit-single-doc.md`：允许按标准结构新增或补齐 `docs/design/frontend-interaction.md`。
- `ai/prompts/review/10-docs-checklist.md`：新增 UI 型项目检查项。

### 命令与 README

- `ai/commands/README.md`：如已有文档生成 / 审查命令，补充前端交互设计适用场景。
- `docs/README.md` 模板说明：在项目形态裁剪表中补充“独立 Web / 移动端演示通常需要交互设计文档”。

## 6. 版本影响

建议作为后续 minor 版本落地。

理由：该变更会影响文档生成、审查口径和派生项目的开发前置条件；但不改变 `docs/00-09` 编号体系，也不强制所有项目新增文档。

## 7. 验收口径

- 模板规则明确说明前端交互设计是条件性详细设计文档，不占用 `docs/00-09`。
- 文档生成提示能根据项目形态判断是否需要 `docs/design/frontend-interaction.md` 或入口拆分文档。
- 审查清单能识别 UI 型项目缺少页面流、状态模型、错误 / 空状态、接口依赖和验收路径的问题。
- 后端 API / CLI / 批处理等无 UI 项目不会被强制要求创建前端交互设计。
- 派生项目在开始前端编码前，能从交互设计文档追溯到 REQ / API / 验收用例。

## 8. 风险与缓解

- **文档负担增加**：定义为条件性文档，只在 UI 复杂度达到触发条件时要求。
- **与 PRD / 技术方案重复**：明确分工，PRD 写产品目标和功能范围，技术方案写技术实现策略，交互设计写用户操作路径和页面状态。
- **过早追求高保真设计**：模板只要求结构化交互设计，不要求视觉稿、像素级 UI 或设计工具产物。
- **项目差异过大**：允许统一 `frontend-interaction.md` 或按入口拆分，模板只规定最低信息结构。
- **AI 自行补交互**：通过“前端编码前必须有交互设计或明确豁免理由”降低临场发挥空间。
